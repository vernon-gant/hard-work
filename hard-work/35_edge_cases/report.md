But in general I see the main idea, it is way better not to poison the data model with some edge edge cases which just overcomplicate the model or even better add some weird encodings of the edge case which are then spread across the codebase. As mentioned restriction of the possible functionality can be considered as an option or the best and the most complicated option if we want to make some process inspectable so that some sneaky edge case can then run some interpretatio on the Free representation and adjust it accordingly, this is again some sort of model complication, but more in technical terms, because the model itself witout all this type machinery remains clean.

# External Id

The idea is that in external systems our participants have external id and in all cases except one system - moni. In the mony case the entry in their system maps to a participant case and for some reason they decided to store the external id there. This results in spread if chains in the grids where when we filter by external id we look not at the participant's external id, but at the participants current
case and there take the special field "MoniId". Nice? With reworked approach where we want the special case not to poison the data model, I would delete this field and just store the id in the participant't external id field during moni import. Or if we really want to distinguish that this ID is from moni, then we can rework the relational model and save is somehow differently. But "id the user sees and searches" but be a self contained concept.

# Gap between two cases

There is a concept of a participant's absence like sick leave, holiday or whatever. Absence also affects the participant's state or better participant state takes into account this fact when deriving the actual state. And then a sneaky snitch comes in - a participant who left and reeneted. This could be a separate type or a concept, but instead there was added an ad hoc type IntermissionReentry with a big chain of ifs which block from deleting these entries, because normal absence entries can be deleted, it becomes also invisible for task triggers for advisors, and many other pages handle it in a specific way. The handling itself it not such a big problem, but using this in the absence data model poisons the model, because it was not thought for this. We could compute it from the cases and add this concept on the case level because it lands in the case bounded context, with a big tention of moving it to the absences.

# Fake Id

There are activity entries in the system like the time recordings, company journals, recomendations and they all lind to the participant. In most cases user can not see the entries of participants it does not have access to, but in some edge case project the requirement was that they can see the entries but should not see the participant data. To achieve this, the server replaces the participant id with a fake id and then we have 4 pages which branch on that fake id and add a placeholder name. Every screen must recognize it... Poisoning is obvious and I do not understand why we just do not compute server side the own state of "hidden participant" on the row and do not represent it with some fixed guid.

# Invented Dead Object

There is a consultation interval evaluation which measures the days between a participant consultations. The normal path is evaluation during the running enrollment. Normally after the cut off date there is a final consultation, but in some project X they do not do it. In that case a fake consultation is added with a hardcoded name and reports and screen filter it out by those names for display or computations. Of course this poisons the data model and I would better make the end of the measured period its own value and not append a consultation for faking and then use this value accordingly so that it does not affect the ordinary computations. Or we can build a computation chain and then in some other rule adjust it based on this new value, but do not integrate this into ordinary flow.
